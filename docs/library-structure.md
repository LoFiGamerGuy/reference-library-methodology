# Library Structure

The directory layout the methodology and tools assume. None of it is enforced — the tools work with any layout that follows these conventions, but adopting the standard layout means everything works out of the box.

## The full layout

```
~/my-reference-library/                 ← your library; lives outside this repo
│
├── INVENTORY.md                        ← auto-generated catalog of all books
├── PLAN.md                             ← optional: roadmap for what to add next
├── README.md                           ← optional: human-facing introduction
├── .env                                ← API keys (gitignored)
│
├── _maps/                              ← per-project tier-ranked reading lists
│   ├── INDEX.md                        ← list of all maps with quick descriptions
│   ├── project-a.md                    ← reading list for project A
│   └── project-b.md                    ← reading list for project B
│
├── _synthesis/                         ← cross-book pattern documents
│   ├── INDEX.md                        ← list of all synthesis docs
│   ├── topic-1-patterns.md             ← what N books say about topic 1
│   └── topic-2-patterns.md
│
├── ai-agents/                          ← books grouped by category
│   ├── book-slug-1/
│   │   ├── content.md                  ← the book's text (or summary, per acquisition tier)
│   │   ├── INSIGHTS.md                 ← extracted patterns (this repo's tools generate)
│   │   ├── metadata.json               ← (optional) machine-readable bibliographic info
│   │   └── images/                     ← extracted images, if any
│   │       ├── chapter-01-fig-01.png
│   │       └── ...
│   ├── book-slug-2/
│   │   └── ...
│   └── ...
│
├── shells-scripting/
│   └── <books>
│
├── linux-no-starch/
│   └── <books>
│
├── ml-oreilly/
│   └── <books>
│
├── web-dev/
│   └── <books>
│
├── data-science/
│   └── <books>
│
└── <other-categories>/
    └── ...
```

## Naming conventions

### Book slugs

Each book lives in `<category>/<book-slug>/`. The slug is:

- **All lowercase**
- **Alphanumeric + hyphens only** (no underscores, no spaces, no special chars)
- **Derived from the title** with stop words removed:
  - "Building Generative AI Agents" → `buildinggenerativeaiagents`
  - "The Linux Programming Interface" → `thelinuxprogramminginterface`
  - "Hands-On Large Language Models, 2nd Edition" → `hands-onlargelanguagemodels-v2`

The slug is what tools query and what users type. Keeping it short and predictable matters.

### Categories

Top-level directories under the library root. Common categories:

| Category | Contents |
|----------|----------|
| `ai-agents` | Books on AI agents, LLMs, agentic systems |
| `ml-oreilly` | ML and data science (often O'Reilly catalog) |
| `app-dev-mobile` | Mobile and app development |
| `web-dev` | Web frontend and backend |
| `shells-scripting` | Bash, PowerShell, scripting languages |
| `linux-no-starch` | Linux internals and systems (often No Starch catalog) |
| `data-science` | Statistical and analytical references |
| `godot-game-dev` | Game dev (Godot specifically) |
| `craft-canon` | Foundational works on craft, design, typography |
| `hacking-security` | Security, offensive and defensive |

You can create new categories as your library grows. Categories should be **broad** — no point creating a category for a single book.

### Reserved directories

Directories prefixed with `_` are conventional and not categories:

- `_maps/` — per-project reading lists
- `_synthesis/` — cross-book pattern docs
- `_pending-download/` (optional) — bundles waiting for extraction
- `_archive/` (optional) — books pulled from active rotation

The `_` prefix is so they sort to the top in alphabetical listings and don't conflict with category names.

## File conventions per book

Each book directory contains:

### `content.md` (required)

The book's text — extracted from EPUB, scanned, or written. Format:

- **YAML frontmatter** at the top (see [`templates/book-frontmatter.template.md`](../templates/book-frontmatter.template.md))
- **Body content** in markdown:
  - For Tier-A books: structured summary, key takeaways, bibliographic notes
  - For Tier-B books: full text with images at `./images/`
  - For Tier-C books: full text plus your annotations

### `INSIGHTS.md` (generated)

Extracted patterns. Generated by `tools/batch_extract_insights.py`. See [insights-extraction.md](./insights-extraction.md) for the methodology.

### `metadata.json` (optional)

Machine-readable bibliographic info. Generated by `epub_to_md.py` if you used it. Useful for cross-referencing but not required by other tools.

### `images/` (if applicable)

Extracted images, named by chapter for legibility:

```
images/
├── ch01-fig-01-architecture-diagram.png
├── ch01-fig-02-state-machine.png
├── ch03-fig-01-flow-chart.png
└── ...
```

Image references in `content.md` should be relative: `![alt text](./images/ch01-fig-01.png)`. The `tools/fix_image_paths.py` utility normalizes paths if you've imported books with various conventions.

## YAML frontmatter schema

The lightweight, load-bearing schema. Every `content.md` should have:

```yaml
---
title: "Full Book Title"
authors: "Author Name(s)"
publisher: "Publisher, Year"
isbn: "ISBN-13 if available"
category: "category-name"
acquisition_tier: "A | B | C"
insights: false                  # set to true once INSIGHTS.md exists
projects: []                     # list of project slugs this book is relevant to
tags: []                         # topic tags
added: YYYY-MM-DD
---
```

Every `INSIGHTS.md` should have:

```yaml
---
title: "INSIGHTS — Book Title"
book: "book-slug"
authors: "Author Name(s)"
publisher: "Publisher, Year"
category: "category-name"
extracted: "YYYY-MM-DD"
extraction_model: "haiku|sonnet|opus"
---
```

Every `_maps/<project>.md` should have:

```yaml
---
title: "Project Name"
slug: "project-slug"
description: "one-sentence description"
status: "active | dormant | archived"
last_updated: YYYY-MM-DD
---
```

Every `_synthesis/<topic>-patterns.md` should have:

```yaml
---
title: "Topic — Cross-Book Synthesis"
sources: ["book-slug-1", "book-slug-2"]
topics: ["topic-tag-1"]
projects: ["project-slug-1"]
generated: YYYY-MM-DD
---
```

These are the load-bearing fields tools query. You can add more (e.g., `notes:`, `priority:`, custom domain fields) — the tools will preserve them and ignore them.

## Locating the library

The methodology tools need to know where your library lives. Three options, in priority order:

1. **`--library /path/to/library`** command-line argument (preferred for one-off runs)
2. **`REFERENCE_LIBRARY_ROOT=/path/to/library`** environment variable (preferred for routine use)
3. **Tools assume `Path(__file__).parent.parent`** — works if you copy the tools into your library's `tools/` subdirectory

The recommended setup:

- Keep this methodology repo wherever you keep your code (`~/code/reference-library-methodology/`)
- Keep your library in a separate location (`~/my-reference-library/` or wherever your data lives)
- Set `REFERENCE_LIBRARY_ROOT` in your shell rc file: `export REFERENCE_LIBRARY_ROOT=~/my-reference-library`

This keeps the methodology updates (via `git pull`) separate from your library content.

## What this layout enables

Once the layout is in place:

- **`load_context.py --project X`** generates a session quick-start by reading `_maps/X.md`, walking it for book slugs, and looking up INSIGHTS in the right category directory
- **`regenerate_inventory.py`** scans every `content.md`, reads the frontmatter, and produces `INVENTORY.md`
- **`mcp_server.py`** indexes every `INSIGHTS.md` for TF-IDF search
- **`batch_extract_insights.py`** scans for `content.md` files without an adjacent `INSIGHTS.md` and runs extraction
- **`tag_library.py`** adds frontmatter tags based on category + slug + chapter keywords

The tools don't enforce the layout — they just look in standard places. If you want to deviate (e.g., books in `<library>/<author>/<book>/` instead of `<library>/<category>/<book>/`), you'll need to fork the tools and adjust the paths.

## Why this specific layout

The categories-as-top-level-dirs is a deliberate choice over alternatives:

- **By author**: a single author often spans multiple categories; their books would cluster awkwardly
- **By topic tag**: a single book often has multiple topic tags; you'd need symlinks
- **Flat**: doesn't scale past ~50 books

Categories are coarse enough that most books fit cleanly into one, and fine enough that the file system stays browseable.
